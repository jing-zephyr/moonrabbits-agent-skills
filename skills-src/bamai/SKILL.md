# bamai · 把脉

> **分工**：laoyeye 的 `socratic-inquiry` 负责"问清问题"（原封不动、独立安装、独立署名）；本 skill 负责问清之后的**增量**——工程需求 + 任务拆分。两层拼起来才是完整的需求工程化。
> **灵魂（甲方 2026-09-29 亲述）**：一位 marketing 背景的人写了一大段自然语言，技术伙伴看不出里面有几个需求；agent 却能拆出二十多个工程化需求，逐条核对正是本意。**本 skill 的价值 = 把业务语言翻译成工程语言，弥合那条沟通鸿沟**——不是对短句做反应，是一段话变成一张能落地的图纸。
> **像中医把脉**：望闻问切问清来意（laoyeye 层）→ **把脉定性，摸出话里真正的病根**（本层）→ **开方交付**，一张能直接施工的图纸。
> 依据：甲方 2026-09-29 拍板口径「laoyeye 的部分是原封不动的 skill 来用，然后后面才是我们自己再往后的」。

## 一、触发判定（先做这个）

**触发**（满足任一）：
- 用户用**一大段自然语言**描述了一个"想做的产品/功能"（可能混乱、自相矛盾、隐含多个需求）；
- 用户明确表达"需求乱/想不清楚/不知道从哪开始"；
- 业务侧与技术侧沟通对不齐，需要把想法翻译成工程语言。

**不触发 → 直接回退**：
- 用户已给出结构化需求 → 跳过提问阶段，直接做 §三 的产出；
- 纯执行类任务（写代码、改文件、跑命令）→ 交回默认进程；
- 问事实类问题（"白瓷的象牙白釉是什么"）→ 交回默认进程，本 skill 不负责查事实。

## 二、第一阶段：交由 laoyeye 问清问题（原封不动）

- **先调用 laoyeye 的 `socratic-inquiry`**（按原技能原文执行，一次只问一个问题、最多六问、够了就停，最后交出一个准确、能接着动手的新问题）；
- 其产出 = "澄清后的准确问题"。本 skill 原样接收，**不重写、不替代**它的提问过程；
- laoyeye 到这里就结束；**我们的增量从 §三 开始**。

## 三、第二阶段：我们的增量（laoyeye 没有的部分）

1. **澄清后的准确问题**（承接 laoyeye 的产出）；
2. **结构化工程需求**（可拆分）：
   ```
   目标 / 受众 / 场景 / 边界（做什么·不做什么）/ 成功标准（可验收）/ 约束与依赖
   ```
3. **任务拆分建议**：带依赖序与每项的可验收标准，能直接交给执行方开工。

## 四、输出契约（固定四段）

```
【澄清后的问题】 —— 一句话，对齐后的真问题
【工程需求】     —— 结构化六项（见 §三）
【任务拆分】     —— 按依赖排序，每项附可验收标准
【待确认清单】   —— 仍不清楚、需要用户/上游拍板的项
```

## 五、硬约束

1. **不编造事实**：需求中出现的事实类断言（市场、法规、技术限制）若无法核实 → 标注「待确认」，不许编；
2. **不替用户做价值决策**：方向取舍必须问，不许"我觉得用户想要 X"；
3. **不打印**任何明文 token / 密钥 / 内网地址；
4. **不改动** checked-in 配置或用户原始文件；
5. 提问阶段输出**短而准**，一次只问一件事。

## 六、方法与署名（合规）

- 提问方法参照 **laoyeye**（github.com/LearnPrompt/laoyeye，MIT）的 `socratic-inquiry`；
- 规则逐字引用见 §二；本 skill **未复制其任何文件**，仅学习方法并以自己的话重写；
- 上游许可：MIT（github.com/LearnPrompt/laoyeye）；本仓仅署名与引用规则，**未包含其源码文件**。
- **我们的增量**：提问之后的「工程需求 + 任务拆分」（laoyeye 只产出"新问题"为止）——这一步是"像产品经理"，也是本 skill 的技术深度所在。
