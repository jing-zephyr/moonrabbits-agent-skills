| 项 | 内容 |
|---|---|
| **skill 名** | `bamai` |
| **中文名** | 把脉 |
| **版本** | 0.1.0 |

## 做什么 / 给谁用

| 做什么 | 给谁用 |
|---|---|
| 把**一大段自然语言想法**拆成结构化工程需求（目标/受众/场景/边界/成功标准/约束），逐条可验收 | 业务侧发起人（市场/运营/产品） |
| 弥合**业务与技术之间的沟通鸿沟**——业务语言 → 工程语言 | 对接的技术团队 / Agent |
| 任务拆分（带依赖序与可验收标准） | 项目排期与执行 |
| 灵魂场景（甲方亲述）：一段 300 字人话 → 二十多个工程化需求，逐条核对正是本意 | 任何"说不清、对不齐"的立项场景 |

## 风险与缓解

| 风险 | 缓解 |
|---|---|
| 需求中混入**编造的事实断言**（市场/法规） | 硬约束：无法核实即标「待确认」，不许编 |
| **替用户做价值决策**（方向取舍） | 硬约束：取舍必须问，矛盾摆出来问 |
| 问太多惹烦用户 | 最多六问；五问清楚就不问第六问（用例 RE-E01/E02） |
| 被误用于事实查询/代码执行 | 负触发明确排除；负向用例 RE-N01/N02 |
| 密钥泄露 | 硬约束：不打印明文 token / 密钥 / 内网地址（用例 RE-S01） |

## 伦理与边界（Ethical）

| 事项 | 立场 |
|---|---|
| 不编造事实 | 需求中的事实类断言无法核实 → 标「待确认」，不许编 |
| 不替用户决策 | 方向取舍由用户拍板；本 skill 只负责把问题问清楚、把选项摆明白 |
| 不越界执行 | 本 skill 只产出需求与拆分，不写业务代码、不动用户文件 |
| 署名合规 | 方法参照明确署名并锁来源，不复制第三方文件（与「不改官方/第三方 skill」红线一致） |
| 密钥 | 不打印任何明文 token / 密钥 / 内网地址 |
